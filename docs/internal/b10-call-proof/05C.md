# B10-MCP-05C: helper/import composition and callable ownership

This checkpoint extends 05B on draft PR #442 for issue #444. Native named plain
handlers can call up to 16 distinct imported project functions at up to 16 static
sites. Aliases and named re-exports use the defining module/function identity and
one consistent schema pair. Targets are ordered by first reachable source site.
Uncalled function bodies and their resource data are not emitted.

A callable may use the existing synchronous pure helpers, including scalar,
readonly record/number-array inputs and literal-bounded loops. Named helper
imports, aliases, re-exports and local helper declarations resolve through the
ordinary project resolver. Each selected helper is validated and emitted through
the same `pure-helper-source` owner used by Router. The canonical Handler IR,
Native plan builder, independent helper validator and generator remain shared.
There is no Entities primitive evaluator or alternate loop implementation.

Callable input provenance comes from its registered schema and is independently
reconstructed from the serialized plan for pure-helper arguments. Helper-local
ownership, readonly borrows, scalar return rules and the 65,536 loop-product cap
remain unchanged. Helpers cannot capture context/constants, call other helpers,
recurse or acquire effects. Imported scalar constants in the callable body are
limited to unwritten `const` string/number/boolean literals (including signed
numeric literals); aliases/re-exports resolve through the same contained graph.
Pass those values as helper arguments when needed. No arbitrary constant
expression evaluator, package target admission or new helper language is added.

Helper descriptors are carried separately from Router metadata for callable
owners. The callable input boundary is attached before independent plan
validation. Only pure helper plans may belong to a callable. Each callable has
its own helper/workspace slots, even when another callable uses the same helper
identity. The top-level resource catalogue deduplicates physical backing blobs
while retaining distinct logical resource bindings. Child plans must match the
caller catalogue and schema definitions exactly.

No nested `ctx.call`, call-in-loop, recursion, awaited calls, effects, dynamic
registry, Router/managed MCP authoring or public API promise is introduced here.
Those boundaries remain with 05D–05G and later application tickets.
