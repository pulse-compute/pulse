## Required local gate

```sh
PULSE_FASTLY_BIN=/absolute/path/to/fastly \
PULSE_VICEROY_BIN=/absolute/path/to/viceroy \
node wasm/scripts/run-wasm-tests.cjs --task kv-conditional-acceptance --no-report
```

Either the existing CLI launcher or an explicitly selected direct Viceroy can
execute the gate. With both variables set, Fastly CLI launches that Viceroy via
`compute serve --file ... --viceroy-path ...`. Missing executables fail before
packing. This dedicated external task has no optional availability mode and is
not silently folded into portable CI. A passing portable release profile alone
does not satisfy K4.

The gate replays K2's runtime/conformance corpus and K3's 195 generated-Wasm ABI
cases, builds the workspace, packs the current 19-package closure, installs exact
tarballs outside the repository with lifecycle scripts disabled, and executes
the installed consumer. A loopback read-only registry keeps Pulse resolution on
that exact closure. Every installed Pulse file is compared with its tarball
before and after execution, including when a semantic gate fails. The consumer
process loads zero workspace product modules. Strict public declaration checks
cover typed values, opaque generations, keyed groups and acknowledgements that
do not expose a new generation.

`run-k4-consumer.cjs` materializes K2's same consumer through ordinary project
configuration, then compiles Node Native, loads Node JavaScript and builds the
Fastly Native artifact through the selected toolchain. No deep product imports
are used in the installed run. The Fastly bytes execute over actual HTTP in
Compute with the physical `k4_catalog` binding.

The black-box schedules use 2, 8 and 16 simultaneous requests, three CAS revisions,
stale tokens, an ABA return to identical value bytes, retained tombstones and
resurrection. Winner values are checked against actual acknowledgements, not
request order. Separate keyed parallel groups exercise the in-handler scheduler.
Maximum value bytes, null, nested envelopes, Unicode and isolated surrogates
round-trip; oversized values remain absent. The real host also rejects seeded
legacy raw JSON and duplicate-member envelopes.

The Node fault corpus proves typed `unknown` after an accepted write loses its
acknowledgement, and `not-stored` before dispatch. A local response-dropping proxy
additionally lets Compute finish, discards the HTTP response, and independently
observes the committed receipt. That is **client transport uncertainty**, not a
fabricated typed KV `unknown`. No mutation is automatically retried.

The full machine record, including failures, module hash/imports, tool binary
hashes and all tarball hashes, appears in the retained task log and
`kv-k4-acceptance.json` in the task artifact directory. `providerReality: true`
means the engine executed; the separate `status` must also be `passed` for
acceptance. It is `failed` for the recorded Viceroy run.
The [captured machine record](k4/viceroy-0.21.0-evidence.json) preserves that
execution's exact artifact identities. It is observed failure evidence, not a
golden result that makes the failure acceptable.

Portable replay is registered in conformance as `kv-conditional-adversarial`;
gate-integrity checks run in unit as `kv-conditional-gates`. Clean-machine
acceptance also runs the installed portable corpus. These lanes remain useful
while the required external gate is blocked.

CLI replay also found stale provider Wasm measurements from the Native changes
already present in K3. The default/optimized Fastly capabilities artifacts now
measure 42,806/35,420 bytes, and the opaque proxy artifacts 30,455/26,287 bytes.
Both variants were rebuilt and validated; the canonical example tables, their

The emitted Native consumer's Wasm SHA-256 is
`4b737584a577c6d8922a068c5b9310701391471f56d1294499f9eddf0b337a75`
(44,926 bytes). It uses `lookup_wait_v2`, `insert`, `insert_wait`, bounded
`fastly_async_io.select`, and WASI monotonic time. K3's pointer-level corpus
independently verifies mode 0, condition mask 32 and the full u64 at offset 24.

[Viceroy 0.21.0's store implementation](https://github.com/fastly/Viceroy/blob/v0.21.0/src/object_store.rs)
checks a supplied generation only inside an `existing`-value condition. When the
key is absent, overwrite mode inserts it. This explains the observed mismatch.
The lookup/condition and final write also acquire the store lock separately;
source inspection therefore raises an atomicity concern. The recorded local
race schedules passed, which does not prove that every host schedule is atomic.

The standalone live comparison below confirms different behavior on deployed
Fastly for these missing-key cases. Upstream clarification or a corrected official engine
must be checked with the unchanged K4 assertions. The source checked during K3
contained the same condition; source mapping alone did not establish acceptance.
Until resolved, report the local gate as failed. The live comparison does not
establish the full Pulse production acceptance described in the T2 handoff.

## Concrete T2 handoff

T2 must provide the reviewed isolated account/service/version, KV store and its
`catalog` binding, the exact Native artifact digest, authentication/authorization
for test writes, and at least two independently located probe agents. T2 also
owns any required service activation; K4 performs no provisioning or activation.
Use the K2 command handler and the same Native build path. Capture the execution
POP and deployment identity at the service-side probe; caller location labels
or arbitrary request headers do not establish cross-location execution.

After T2 authorization, run:

```sh
node wasm/test/kv/run-k4-deployed.cjs --driver /absolute/path/to/reviewed-T2-probe-driver.cjs
```

The driver is a trusted test harness, not a new product provider or public API.
It exports async `createProbes()` returning:

```js
{
  identity: { serviceId, serviceVersion, storeId, moduleSha256 },
  probes: [{
    id,
    async invoke(command, { signal }) {
      // Perform exactly one authenticated remote invocation, without retries.
      return { result, metadata };
    },
    async loseResponse(command, { signal }) {
      // Required on the first probe: dispatch once through a controlled relay,
      // drop the application response, retain independent service-side metadata.
      return { outcome: 'response-lost', metadata };
    }
  }],
  readTimeoutMs: 30000,
  async close() { /* stop probe resources; retain evidence and authority keys */ }
}
```

Every metadata record supplies the exact expected service, version, store and
artifact fields, plus `pop` and a unique `requestId`. The transport must honor
the supplied abort signal and bound its own response bytes. The runner applies
a 15-second invocation deadline, checks identities/unique POPs before writes,
rejects cached receipts or POP changes, and emits no keys, generations, candidate
bytes or authentication values in request summaries. It records the unique test
key prefix so an operator can account for retained test data.

The deployed corpus runs three simultaneous creation/CAS schedules across the
verified POPs. It checks acknowledged winners, value/generation pairing, stale
exclusion, missing-key rejection and conditional tombstones. Bounded read-only
polling accommodates stale reads; visibility timeout is inconclusive, not a
strong freshness promise. Unexpected/unknown mutation acknowledgements fail the
acceptance schedule without retry/rebase. A controlled dropped response followed
by independent cross-location receipt observation covers client uncertainty.
Authority keys remain present, including tombstones. Physical deletion, expiry,
cross-key transactions, restart durability and exhaustive global consistency are
outside this bounded evidence.

The driver and live environment are intentionally absent until T2 supplies those
inputs. Unit fixtures verify this runner's rejection of mixed identities, same
POP evidence, replayed receipts, missing fault capability and unknown writes;
those fixtures are not deployed evidence. A future passing deployed record does
not waive the user's required local Compute gate.
