# O3 paused: Fastly JavaScript response-header boundary

O3 starts from `latest` at `01ac67677882ba267dbf563ea8e5b5eecec5dd3a`,
which merged O2 PR #5. Its intended completion remains bounded PUT plus
HEAD/GET/PUT on Node and Fastly, JavaScript and Native, through one canonical
consumer. O4 still owns release membership and packed acceptance.

The first provider feasibility check found information loss below S3's
contract. Per the user's instruction to pause at abstraction leaks, dependent
implementation is paused. This checkpoint adds a reproducible probe and a
resolution proposal. It does not implement PUT, enable JavaScript S3, change
O1's metadata contract, or claim O3 acceptance.

## Reproduction and observed result

Run from the repository root with lockfile-pinned dependencies installed and
an executable Viceroy selected:

```sh
PULSE_VICEROY_BIN=/absolute/path/to/viceroy \
  node wasm/test/s3/probe-fastly-javascript-headers.cjs
```

The probe compiles `fastly-javascript-header-probe.mjs` using the repository's
exact `@fastly/js-compute` version. It starts a local raw HTTP origin and runs
the resulting Fastly JavaScript Wasm through the provider's existing Viceroy
launcher. Each response comes from that origin once with cache bypass. No
bucket, credentials, remote service or deployment is involved. Temporary
files, sockets and processes are released. A missing compiler/runtime or a
failed assertion fails the command; nothing is silently skipped.

Observed on 12 September 2026 with SDK **3.43.1** and Viceroy **0.20.1**:

| Origin input | Required S3 interpretation | Fastly JavaScript observation |
| --- | --- | --- |
| One `etag: one, two` | Valid opaque ETag | `one, two` |
| Two fields, `etag: one` and `etag: two` | Protocol failure: duplicate ETag | `one, two` |
| One `content-type: one, two` | Valid opaque response metadata | `one, two` |
| Two content-type fields, `one` and `two` | Protocol failure: duplicate metadata | `one, two` |
| 18,209 bytes of response header fields | Protocol failure: exceeds 16,384 bytes | 513 bytes after projection |

The single-field and duplicate-field responses have identical observable
status, `Headers.get()` results and `Headers.entries()` results. The current
S3 metadata validator correctly rejects the raw duplicate pairs and accepts
the valid single fields. Given the projected pairs, it accepts both. The
same projection hides the aggregate header-budget violation.

The command exits successfully only when it reproduces these gaps and prints
`status: blocker-confirmed` with `s3Acceptance: false`. It is an explicit
feasibility probe, outside the passing S3 acceptance profiles. When the
capability is resolved, replace these expected blocker assertions with
positive metadata-boundary acceptance before enabling the target.

## Owning boundary

The pinned SDK tag points to Fastly runtime commit
[`7d3a3394fc13c20c89359d4257d43b8562dcbf72`](https://github.com/fastly/js-compute-runtime/tree/7d3a3394fc13c20c89359d4257d43b8562dcbf72).
Its [request/response implementation](https://github.com/fastly/js-compute-runtime/blob/7d3a3394fc13c20c89359d4257d43b8562dcbf72/runtime/fastly/builtins/fetch/request-response.cpp)
uses StarlingMonkey's `Headers`, pinned to
[`3c2dbf48f5b13792d5465de4f5f817b20de43fab`](https://github.com/bytecodealliance/StarlingMonkey/tree/3c2dbf48f5b13792d5465de4f5f817b20de43fab).
That [Headers implementation](https://github.com/bytecodealliance/StarlingMonkey/blob/3c2dbf48f5b13792d5465de4f5f817b20de43fab/builtins/web/fetch/headers.cpp)
joins ordinary repeated values for both host-backed `get()` and iteration.
Only Set-Cookie has a public multiple-value accessor. Fastly's underlying
[host API](https://github.com/fastly/js-compute-runtime/blob/7d3a3394fc13c20c89359d4257d43b8562dcbf72/runtime/fastly/host-api/host_api.cpp)
can enumerate individual values; the information is lost at the JavaScript
API boundary.

Node's existing S3 transport uses `IncomingMessage.rawHeaders`. Fastly Native
uses `fastly_http_resp.header_names_get` and `header_values_get`, preserving
each field for package validation. The missing capability is specifically
the Fastly JavaScript provider's access to bounded raw response metadata.
Compiler orchestration, Assets and Catalog cannot repair information already
erased by this projection. Splitting commas cannot distinguish the two valid
input shapes above. Changing opaque metadata or the aggregate header limit
would change the agreed S3 contract.

## Proposed prerequisite and resumption gate

Preserve O1 and add an information-preserving response-metadata capability at
the Fastly SDK/provider boundary. This proposal requires an SDK capability;
it is not an existing callable JavaScript API or a completed implementation.
The provider-facing contract must:

1. Enumerate individual response header names and raw value bytes, retaining
   multiplicity before concatenation or text decoding.
2. Enforce the 16,384-byte aggregate budget during bounded enumeration;
   report incomplete or over-limit metadata without an unbounded intermediate
   JavaScript `Headers` materialization.
3. Retain the observed final HTTP status independently of metadata errors.
4. Leave strict UTF-8 interpretation and selected-field semantics in S3,
   with provider-owned response/body cleanup and no application raw handle.
5. Be explicitly selected and verified in the pinned Fastly JavaScript
   toolchain; preserve the existing Native realization and fallback policy.

A supported upstream API is preferable. Maintaining an SDK extension would
introduce a toolchain ownership and update obligation that needs an explicit
architecture decision before becoming a production dependency.

Resume O3 only after a real SDK/Viceroy probe distinguishes the two header
shapes and rejects excessive raw headers through that capability. Then
complete Crypto-owned Web Crypto output primitives, PUT lowering/signing,
both provider lifecycles, and the canonical four-target write/inspect/read
consumer. Cancellation, deadlines through body completion, payload integrity
and uncertain writes remain mandatory O3 checks; this header probe does not
establish them. O2 remains the implemented capability baseline.
